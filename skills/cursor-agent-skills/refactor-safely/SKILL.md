# 安全重构

## 何时使用

- 用户要求重构、重写、整理代码
- 大范围调整目录结构或模块划分
- 依赖/框架大版本升级
- 需要改动但没有足够测试覆盖时

## 铁律

> **重构不改变外部行为。**
> 如果行为变了，那叫「重写」或「改需求」，不是重构——必须跟用户明确区分，走需求变更流程。

第二铁律：**没有测试网就不要重构。先补测试，再动手。**

## 步骤

### 阶段一：明确目标与边界（先问清楚）

动手前必须确认：

| 问题 | 为什么重要 |
|------|-----------|
| 重构的目标是什么？ | 「让代码更好」不是目标，「把 2000 行的 x.js 拆成 5 个模块」才是 |
| 范围到哪里为止？ | 防止无限扩散 |
| 行为允许变化吗？ | 不允许 = 重构；允许 = 重写，需走需求流程 |
| 有没有测试覆盖？ | 没有就先补 |
| 可回滚吗？ | 每一步都要能 `git revert` |

**如果目标含糊或范围会无限扩散，先停下来问用户。**

### 阶段二：补测试网（覆盖率不足时必做）

优先级：

1. **公共接口 / 对外的行为**——契约测试，最重要
2. **即将被改动的模块**——行为快照测试（characterization test）
3. **复杂的边界逻辑**

行为快照测试的写法（针对没有测试的老代码）：

```js
// 先记录「当前行为」，不管它对不对
test('characterization: 旧的 calculate 行为快照', () => {
  expect(calculate({ a: 1, b: 2 })).toBe(3);
  expect(calculate({ a: -1 })).toBe(0);
  expect(calculate({})).toBe(0);
});
```

**关键**：如果当前行为是错的，先**单独记录**这个已知 bug，重构时保留该行为，之后单独修——**绝不在重构中顺手改行为**。

确认测试网：

```bash
<跑测试命令>   # 全绿才算网织好了
```

### 阶段三：小步重构

每一步遵循：

```
改一点点 → 跑测试 → 通过 → 提交
   ↓
不通过 → revert 这一步 → 换更小的步子
```

**单步粒度参考**：

| 重构类型 | 合适粒度 |
|---------|---------|
| 重命名 | 一次一个符号（或一次一个文件内的所有引用） |
| 提取函数 | 一次提取一个 |
| 移动文件 | 一次移动一个文件 + 修引用 |
| 改数据结构 | 一次一个字段 |
| 依赖升级 | 先升一个包，跑通再下一个 |

**每步之后**：

```bash
<跑测试>          # 必须全绿
git add -A && git commit -m "refactor(<scope>): <这一步做了什么>"
```

### 阶段四：常用重构手法（按风险从低到高）

| 手法 | 风险 | 说明 |
|------|------|------|
| 重命名变量/函数 | 极低 | 用 IDE 的 rename symbol，别手动替换 |
| 提取常量 | 低 | 消魔法值 |
| 提取函数 | 低 | 函数过长时 |
| 内联函数 | 低 | 过度抽象时 |
| 消除重复 | 中 | 三次原则：出现三次才抽 |
| 移动文件/改目录 | 中 | 注意循环依赖 |
| 提取接口 / 拆模块 | 高 | 先画依赖图 |
| 改数据结构 | 高 | 需考虑持久化数据迁移 |
| 改并发模型 | 极高 | 单独评估，不要混在重构里 |

**警惕循环依赖**：拆模块前先画依赖图，确认拆分后不会 A→B→A。

### 阶段五：收尾

- [ ] 测试全绿
- [ ] 行为无变化（跑一遍关键路径的手工验证）
- [ ] 无新增依赖
- [ ] 无遗留的临时兼容代码（除非有迁移计划）
- [ ] 提交历史是**一串小而清晰的 refactor 提交**，不是一坨
- [ ] 跑 `code-review-gate`
- [ ] 跑 `data-compliance-guard`

### 阶段六：输出报告

```markdown
## 重构报告

**目标**：xxx
**范围**：涉及 N 个文件
**行为变化**：无（或：有，见下）

### 补测试
- 新增测试：N 个（覆盖率 x% → y%）

### 提交序列
| # | commit | 这一步做了什么 | 测试 |
|---|--------|--------------|------|
| 1 | `abc1234` | 提取 xxx 函数 | ✅ |
| 2 | `def5678` | 移动 yyy 文件 | ✅ |

### 验证
- [ ] 测试全绿
- [ ] 关键路径手工验证通过
- [ ] 行为无变化

### 未做 / 后续建议
- <明确列出这次没做但建议做的事，附上理由>
```

## 边界（Do NOT）

- **不要在重构中改行为**——这是最高频的事故来源
- **不要在重构中修 bug**——单独一个 `fix` 提交
- **不要在重构中加新功能**——单独一个 `feat` 提交
- **不要一次改一大片**——改到一半发现要动 20 个文件，说明粒度太大，先停下来拆
- **不要在没测试网时重构核心模块**——先补测试
- **不要为了「更优雅」引入新抽象**——抽象有成本，三个以上用例才值得
- **不要删除「看起来没用」的代码**除非能证明无引用——先全局搜索
- 一次重构失败就 `git revert` 回退，**不要试图在坏掉的基础上继续改**
