# 系统化排障

## 何时使用

- 遇到报错、崩溃、异常行为
- 测试失败
- 构建/启动失败
- 用户说「有 bug」「跑不起来」「为什么这样」

## 铁律

> **没有复现，就没有修复。**
> 复现不了的问题，先想办法复现，不要猜。

## 步骤

### 阶段一：稳定复现（不可跳过）

1. **收集信息**
   - 完整错误信息（**不要用「报错了」概括，要原文**）
   - 复现步骤（最小步骤）
   - 环境：OS、运行时版本、分支、commit
   - 什么变了：最近改了什么？依赖升级过吗？
   - 是必现还是偶现？频率多少？

2. **构造最小复现**
   - 剥掉无关步骤，找到**最小触发路径**
   - 能写成一个测试最好——**复现用例 = 未来的回归测试**

3. **确认复现**

```
复现确认：
- 最小步骤：1) ... 2) ... 3) ...
- 期望结果：xxx
- 实际结果：xxx
- 复现率：必现 / N 次中出现 M 次
```

**如果复现不了**：明确告诉用户「暂时无法复现」，然后列出下一步可行的取证手段（加日志、提高日志级别、加监控、灰度观察），**不要凭猜测改代码**。

### 阶段二：二分定位

**不要通读代码猜**。用二分法把范围缩小：

| 手段 | 怎么用 |
|------|--------|
| **git bisect** | 之前是好的、现在坏了 → 二分定位到具体 commit |
| **删代码法** | 注释掉一半逻辑，看问题是否消失 |
| **打点法** | 在关键路径加日志，确认数据在哪一步开始不对 |
| **边界法** | 确认是输入问题、处理问题还是输出问题 |
| **环境对照** | 换个环境/换个数据/换个用户，看是否仍复现 |

```bash
git bisect start
git bisect bad HEAD
git bisect good <已知正常的 commit>
# 按提示测，最后
git bisect reset
```

**每一步都要有证据**，记录：

```
定位过程：
1. 确认错误发生在 <模块/函数>：证据 = <日志/断点输出>
2. 排除 <假设 A>：证据 = <做了什么验证，结果如何>
3. 排除 <假设 B>：证据 = ...
```

### 阶段三：找根因

**区分症状与根因**：

| | 例子 |
|---|---|
| 症状 | 页面白屏 |
| 直接原因 | `user.profile.name` 读取时 `profile` 为 undefined |
| **根因** | 用户资料接口在权限不足时返回 `{ id }` 而不含 `profile`，前端未处理该分支 |

**连问五个为什么**，直到找到「改掉它，这类问题不会再发生」的那一层。

只修症状 = 同一个 bug 换个地方再犯。

### 阶段四：最小修复

原则：

- **改最少的代码**
- **不顺手重构**（重构另开 `refactor-safely`）
- **不顺手「优化」无关部分**
- 如果正确修复需要大改，**先停下来跟用户确认方案**

修完后自问：

- [ ] 这个修复会不会引入新问题？
- [ ] 边界情况处理了吗？（空值、极值、并发、超时）
- [ ] 同类问题在别处存在吗？（搜索相似代码）

### 阶段五：补回归测试

**每个修复都要有一个能失败的测试**：

```js
test('权限不足时不应读取 profile 导致白屏', () => {
  const res = { id: '1' }; // 无 profile 字段
  expect(() => render(<UserCard data={res} />)).not.toThrow();
});
```

确认测试**在修复前会失败、修复后通过**——否则这个测试没价值。

### 阶段六：输出报告

```markdown
## 排障报告

**症状**：xxx
**影响范围**：xxx（哪些场景/用户受影响）

### 根因
<一句话根因>
证据：<日志/代码位置/验证过程>

### 为什么会发生
<连问为什么的链条>

### 修复
- 改动：<文件:行号>，改了什么
- 为什么这样改：<理由>

### 验证
- [ ] 最小复现用例通过
- [ ] 新增回归测试：通过（且修复前失败）
- [ ] 相关用例全绿：<结果>
- [ ] 手工验证：<步骤与结果>

### 同类排查
- 搜索了 <关键词>，在 <位置> 发现 N 处相似写法，其中 M 处有同样风险
```

## 边界（Do NOT）

- **不要没复现就改代码**（唯一例外：问题明显且有充分日志证据）
- **不要连续三次「试试这个」式盲改**——三次无效就停下来，回到阶段一
- **不要只修症状不修根因**
- **不要把异常吞掉当修复**（`try {} catch {}` 不是修复）
- **不要顺手重构无关代码**——扩大改动面 = 扩大风险
- **不要声称「应该好了」**——必须给出**实际执行结果**
- **不要修改测试来让它通过**，除非能证明测试本身是错的
