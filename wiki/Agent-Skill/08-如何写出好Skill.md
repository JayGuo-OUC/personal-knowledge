# 如何写出好 Skill

## 摘要

写 Skill 的正确顺序是**先定义 2-3 个具体用例，再动手写文件**。核心原则只有两条：**判断写 Markdown，确定性逻辑写脚本**；**description 是召回索引，不是简介**。最常见的失败不是写得不够多，而是 description 写坏了导致永不触发、或正文塞太多导致关键指令被稀释。

## 正文

### 第一步：先写用例，别急着写文件

Anthropic 官方流程明确要求：动手前先列 2-3 个**具体用例**，每个用例写清四件事。

```
用例：项目 Sprint 规划
触发：用户说「帮我规划这个迭代」或「创建迭代任务」
步骤：1. 从 Jira 拉当前状态  2. 分析团队速率  3. 排优先级  4. 建任务
产物：一份排好的迭代计划，任务已创建
```

问自己四个问题：

1. 用户想**达成什么**？
2. 这需要**哪几步**？
3. 需要**什么工具**（内置 or MCP）？
4. 有哪些**领域知识或最佳实践**是模型不知道的？

四个问题答不上来，说明你还不清楚要做什么——先别写。

### 第二步：写 description（最重要）

**公式**：`做什么 + 何时用`

| | 示例 |
|---|---|
| ❌ 差 | `Helps with PDFs.` |
| ✅ 好 | `Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction.` |
| ❌ 差 | `处理代码。` |
| ✅ 好 | `按团队六维清单评审代码（安全/敏感信息/合规/性能/可维护性/依赖）并输出留痕报告。当用户要求评审、审查、审计代码，或提交 PR 前需要检查时使用。` |

三条检验标准：
- 有**具体动词**（提取/填写/合并/评审）而非泛动词（处理/帮助）
- 有**触发关键词**（PDF、表单、评审、PR）
- 有**使用场景**（「当用户…时使用」）

### 第三步：搭正文骨架

```markdown
---
name: xxx
description: 做什么 + 何时用
---

# 标题

## 何时使用
- 触发条件 A
- 触发条件 B

## 步骤
1. 第一步（含具体命令/工具）
2. 第二步
3. 第三步

## 示例
输入 → 输出 的完整例子（至少一个）

## 边界（Do NOT）
- 明确禁止的行为
- 出错时的兜底做法
```

**四个部分缺一不可**，尤其「Do NOT」——没有边界的技能，模型会在边界情况自由发挥。

### 核心原则：判断 vs 确定性

这是区分「能用」与「好用」的分水岭。

| 特性 | 放 Markdown（模型判断） | 放脚本（确定性执行） |
|------|----------------------|-------------------|
| 需要理解语义 | ✅ | ❌ |
| 每次结果必须一致 | ❌ | ✅ |
| 需要读大量数据 | ❌（会污染上下文） | ✅（只有结果进上下文） |
| 逻辑复杂但不便描述 | ❌ | ✅ |
| 需要灵活应变 | ✅ | ❌ |

一句话总结（来自一线工程师）：

> 技能 = **给 Agent 的自然语言描述** + **显式确定的可执行脚本**。

### 反模式清单

| 反模式 | 症状 | 修法 |
|--------|------|------|
| **巨型 SKILL.md** | 超 500 行且不拆 references | 拆 |
| **无结构** | 一坨文字没小标题 | 加 `#`/`##` |
| **description 空泛** | 「帮助代码」「处理文档」 | 补动词 + 场景 |
| **关注点混杂** | SKILL.md 里内联脚本 | 抽到 `scripts/` |
| **没有示例** | 只有指令没有输入/输出样例 | 至少补一个完整示例 |
| **没有约束** | 缺 Do NOT / 边界段 | 补 |
| **引用链过深** | A.md → B.md → C.md | 拍平 |
| **假设独占** | 「总是先执行 X」 | 改为「在本技能范围内」 |

### 评测：怎么验证技能好不好

Anthropic 官方方法：

1. 准备一组评测问题
2. **一半应该触发该技能，一半不应该**
3. 跑一遍看命中率

只看「该触发的触发了没」会漏掉误触发问题。两类都要测。

| 评测项 | 通过标准 |
|--------|---------|
| 应触发的用例 | ≥80% 命中 |
| 不应触发的用例 | ≤10% 误触发 |
| 加载后是否照做 | 关键步骤 100% 执行 |
| 输出格式 | 符合模板 |

### 迭代方法

1. **先跑起来**：最小可用版本（frontmatter + 10 行步骤）
2. **真实场景跑 3 次**，记录哪里没照做
3. **补指令**：模型在哪一步跑偏，就在那一步加约束或示例
4. **补示例**：模型输出格式不对，就给一个完整正例
5. **拆文件**：正文超 300 行开始考虑拆 references
6. **进 PR**：让队友用一遍

不要一上来就追求完美——**Skill 的迭代成本极低（改个文件即时生效），这本身就是它最大的优势**。

### 质量自检清单

发布前过一遍：

- [ ] `name` 合法且与目录名一致
- [ ] `description` 含「做什么 + 何时用」，有触发关键词
- [ ] 正文 < 500 行
- [ ] 有「何时使用」段
- [ ] 步骤是有序的、可执行的
- [ ] 至少一个完整输入/输出示例
- [ ] 有「Do NOT」/边界段
- [ ] 引用路径相对、只深一层
- [ ] 脚本自包含、有错误提示、有参数校验
- [ ] `skills-ref validate ./my-skill` 通过
- [ ] 已提交 git
