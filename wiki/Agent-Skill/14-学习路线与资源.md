# 学习路线与资源

## 摘要

四阶段路线：**读懂 → 会写 → 写好 → 能治理**。个人从「装一个现成的」开始，团队从「把一条最痛的流程固化成技能」开始。核心资源是 `agentskills.io` 规范（很短，值得通读一遍）与 `anthropics/skills` 官方示例库（读 5 个真实技能比读 10 篇教程有用）。

## 正文

### 四阶段路线

#### 阶段一：读懂（约 1 小时）

| 顺序 | 做什么 |
|------|--------|
| 1 | 读 [[01-Skill是什么]]，建立「文件夹 = 能力包」的心智 |
| 2 | 读 [[03-SKILL.md结构与frontmatter详解]]，记住只有 2 个必填字段 |
| 3 | 读 [[04-渐进式披露机制]]，理解三层加载 |
| 4 | 通读 [agentskills.io/specification](https://agentskills.io/specification)，**全文很短，一次读完** |

**验收**：能说清「启动时加载什么、命中后加载什么」。

#### 阶段二：会写（约 半天）

| 顺序 | 做什么 |
|------|--------|
| 1 | 在 Cursor 里敲 `/create-skill`，跟着引导做第一个技能 |
| 2 | 改用手动方式重写一遍，理解目录与 frontmatter |
| 3 | 读 [[08-如何写出好Skill]]，按反模式清单自查 |
| 4 | 用 `/skill-name` 显式调用验证 |
| 5 | 用自然语言触发，看是否自动命中 |

**验收**：有一个技能能在真实任务中被自动触发且执行正确。

#### 阶段三：写好（约 1-2 周）

| 顺序 | 做什么 |
|------|--------|
| 1 | 读 `github.com/anthropics/skills` 里的 5 个官方示例，**对比自己的写法** |
| 2 | 给技能加 `scripts/`：把确定性逻辑从 Markdown 里抽出来 |
| 3 | 给技能拆 `references/`：正文超 300 行就拆 |
| 4 | 做触发评测：一半该触发、一半不该触发 |
| 5 | 读 [[07-Skill与Rules-Commands-MCP-Subagent对比]]，把用错的工具换对 |

**验收**：技能触发准确率高，正文精简，关键逻辑在脚本里。

#### 阶段四：能治理（持续）

| 顺序 | 做什么 |
|------|--------|
| 1 | 读 [[12-Skill安全与企业合规]]，建立准入与评审流程 |
| 2 | 建内部技能 Git 仓库，禁装外部市场技能 |
| 3 | CI 里跑 `skills-ref validate` |
| 4 | 建技能清单（SBOM）：名称、来源、负责人、评审日期 |
| 5 | 定期体检：哪些技能从没被触发过？哪些描述需要更新？ |

**验收**：技能有清单、有负责人、有评审记录、有版本固定。

### 给团队负责人的落地顺序

不要一上来就推广「大家都来写技能」。有效路径是：

1. **先找最痛的那条流程**（通常是发布流程或评审标准）
2. **自己写一个，自己用一周**，改到顺手
3. **给 2-3 个人试用**，收集「哪里没照做」
4. **修好后进仓库**，在团队会上演示 10 分钟
5. **再写第二个**

采纳率的关键不是技能有多全，而是**第一个技能解决的是不是真痛点**。

### 常见误区（避坑）

| 误区 | 真相 |
|------|------|
| 「Skill 能让模型变强」 | 不能。它只改上下文，不改权重 |
| 「描述越长越好」 | 不是。写清「做什么 + 何时用」即可，长了反而稀释 |
| 「把规则全改成 Skill」 | 不该。常驻约束用 Rule 更合适 |
| 「技能越多越好」 | 不是。从未触发的技能是纯负担，定期清理 |
| 「装社区技能省事」 | 有真实供应链风险，13.4% 含严重问题 |
| 「写了就完事」 | 不是。要评测触发率，要迭代 description |
