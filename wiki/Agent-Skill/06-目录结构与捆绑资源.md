# 目录结构与捆绑资源

## 摘要

一个技能 = `SKILL.md`（必需）+ `scripts/`（可执行代码）+ `references/`（按需文档）+ `assets/`（模板/图片/数据）+ 任意其它文件。核心设计原则是**关注点分离**：判断写 Markdown，确定性逻辑写脚本，重型文档外置。技能目录应当**提交进 git**，像 ESLint 配置一样在 PR 里评审。

## 正文

### 标准结构

```
skill-name/                    # 必须与 name 一致
├── SKILL.md                   # 必需：元数据 + 指令
├── scripts/                   # 可选：可执行代码（⚠️ 会触发安全审查）
│   ├── deploy.sh
│   └── validate.py
├── references/                # 可选：按需加载的文档
│   ├── REFERENCE.md
│   ├── api-guide.md
│   └── examples.md
└── assets/                    # 可选：静态资源
    ├── config-template.json
    └── diagram.png
```

规范允许**任意额外文件和目录**，上面只是推荐约定。

### 三类资源的分工

| 目录 | 放什么 | 进上下文吗 | 典型用法 |
|------|--------|-----------|---------|
| `scripts/` | Python / Bash / JS 可执行代码 | ❌ 只有执行结果进 | 数据转换、批量校验、调外部 CLI |
| `references/` | 详细技术文档、API 说明、长表格 | ✅ 按需读取 | 「详见 references/API.md」 |
| `assets/` | 模板、图片、schema、查找表 | ✅ 按需读取 | 「从 assets/template.json 开始改」 |

**`scripts/` 是最被低估的一层**。它几乎零上下文成本（源码不进提示词），且每次执行结果完全一致。适合放：

- 复杂的文本/数据解析
- 需要多次重试的外部调用
- 你不希望模型「每次自由发挥」的确定性逻辑

### scripts/ 编写要求（官方规范）

- **自包含**，或明确写清依赖
- **有用的错误信息**（出错时要能指导下一步）
- **优雅处理边界情况**（空输入、非法参数、网络失败）
- 头部注释写清用法

示例骨架：

```python
#!/usr/bin/env python3
"""validate.py — 校验迁移脚本是否符合规范。

用法: python scripts/validate.py <migration-file>
退出码: 0=通过, 1=发现错误
依赖: Python 3.9+, 无第三方包
"""
import sys

def main(path: str) -> int:
    if not path:
        print("错误: 缺少参数。用法: python scripts/validate.py <file>", file=sys.stderr)
        return 1
    # ...
    return 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1] if len(sys.argv) > 1 else ""))
```

### references/ 拆分原则

| 原则 | 反例 | 正例 |
|------|------|------|
| 按主题拆，不要一个巨文件 | `ALL.md`（3000 行） | `api-guide.md`、`examples.md`、`troubleshooting.md` |
| 只深一层 | `references/a/b/c.md` | `references/api-guide.md` |
| 避免引用链 | A → B → C | SKILL.md 直接指向 A、B、C |
| 命名清晰 | `doc1.md` | `error-handling.md` |

### 引用规则

在 `SKILL.md` 里用**从技能根出发的相对路径**：

```markdown
详细字段说明见 [references/API.md](references/API.md)。

执行校验：
python scripts/validate.py
```

规范明确要求：**保持引用只有一层深，避免深层嵌套的引用链**。

### 组合性

规范强调：**Claude 可以同时加载多个技能**（Cursor 同理）。所以写技能时**不要假设「只有我一个」**：

- ❌ 「总是先执行 X」——可能与别的技能冲突
- ✅ 「在本技能范围内，执行 X」
- ❌ 定义通用术语（可能与别人重名冲突）
- ✅ 用具体、唯一的措辞

### 版本控制与团队分发

这是 Skill 相对「提示词模板文档」的杀手锏：

| 能力 | 怎么做 |
|------|--------|
| **版本化** | `.cursor/skills/` 直接进 git |
| **评审** | 改技能走 PR，跟改 ESLint 配置一样对待 |
| **分发** | 推到 GitHub → 队友通过 Remote Rule 导入；或直接 clone 仓库 |
| **回滚** | git revert |
| **审计** | git log 能看到谁在什么时候改了红线 |

> ⚠️ **注意**：Cursor 的**全局**技能（`~/.cursor/skills/`）**不会**自动同步到 Cloud Agents、远程 SSH 会话、self-hosted worker。团队规范必须放**项目级**目录并进 git。

### 组织多个技能

```
.cursor/skills/
├── shipping/              # 分类目录，纯组织用
│   ├── land-it/SKILL.md           # 技能名 = land-it
│   └── careful-merge/SKILL.md
├── debugging/
│   └── using-datadog/SKILL.md
└── workflow/
    └── tdd/SKILL.md
```

- Cursor **递归遍历**技能根目录，子目录随便套
- 技能的**身份来自包含 SKILL.md 的那一层目录名**，不是上层分类目录
- 也支持**嵌套项目目录**（monorepo）：`apps/web/.cursor/skills/` 下的技能**自动只作用于** `apps/web/` 内的文件
