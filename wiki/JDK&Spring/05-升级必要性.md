# 升级必要性论证（JDK 21 + Spring Boot 4）

## 摘要

从「JDK 8 + Spring Boot 2.3」升级到「JDK 21 + Spring Boot 4」，**首要驱动力不是新特性，而是风险敞口的关闭**：Boot 2.3 已于 2021-05 停止开源支持、2022-08 商业支持终止，JDK 8 的 Oracle 免费更新早已结束，二者叠加意味着**新披露漏洞无官方补丁**。对政府、工业、水务这类强合规行业，这不是技术选型问题，而是能否通过等保测评与供应链安全审查的问题。在此之上，升级才谈收益：容器原生适配、虚拟线程带来的并发量级提升、内建可观测性与弹性能力、以及与信创生态的对接。

---

## 一、不做会怎样：风险侧（决定性）

### 1.1 组件已全面 EOL，安全补丁断供

| 组件 | 当前使用 | OSS 支持状态 |
|------|---------|-------------|
| Spring Boot 2.3 | 2020-05 发布 | **2021-05 EOL**；商业支持 **2022-08 终止** |
| Spring Framework 5.2 | 随 Boot 2.3 | 早已停止维护 |
| JDK 8 | 2014-03 发布 | Oracle 免费更新**已终止**；首要支持 2022-03 结束 |

后果链条很直接：

```
新 CVE 披露 → 官方不回补丁 → 漏洞扫描报红且无修复方案
           → 等保测评/安全审查不通过 → 政企项目验收与续约受阻
```

⚠️ **这是最硬的一条。** 政府与水务项目通常有明确的漏洞整改时限要求，「依赖组件已停止维护，无补丁可用」在测评中属于难以豁免的扣分项。相比之下，升级的工时成本是可预算的一次性投入，而合规风险是持续暴露的。

### 1.2 供应链与依赖债

Boot 2.3 生态中常见的 springfox（Swagger）、Fastjson 1.x、老版本 Druid/PageHelper 等，或已停更、或长期高危。依赖树越老，可用的安全版本越少，最终会陷入「升一个崩一串」的被动局面。

### 1.3 人才与技术债

- 新招聘的 Java 开发者默认接触的是 Records、虚拟线程、Lambda DSL 等现代写法，老栈的学习与维护意愿持续下降
- 新中间件、新 SDK、新云服务的官方支持普遍以 JDK 17+ / jakarta 为基线，老栈的**可选技术面在持续收窄**
- AI 辅助编程工具（如已选定的 Cursor）的训练语料同样偏向现代栈，老栈上获得的生成质量与可维护性更差

### 1.4 时间窗口正在关闭

| 时间 | 事件 | 影响 |
|------|------|------|
| **2026-09（本月）** | Oracle JDK 21 最后一个 NFTC 免费更新 | 此后 Oracle JDK 21 的更新需商业订阅 |
| **2026-12-31** | Spring Boot 4.0 OSS 支持结束 | 落在 4.0 上很快就要再升一次 |
| 已发生 | Spring Boot 3.x 全系 EOL（3.5 于 2026-06-30 结束） | 现在升级若落 3.x = 落在已停更版本 |

> ⚠️ **因此建议直接定在 Spring Boot 4.1，不要落 3.x。** 落 3.x 等于刚升级就要规划下一次升级。

## 二、做了能得到什么：收益侧

### 2.1 云原生适配（架构层面的根本改善）

升级后，应用才真正「为云而设计」，见 [[01-云原生概览]] 的四大特征。

| 云原生的要求 | JDK 8 + Boot 2.3 的困境 | JDK 21 + Boot 4 的改善 |
|-------------|----------------------|----------------------|
| **容器内存感知** | JVM 读宿主机内存，`-Xmx` 常超 Pod limit → 频繁 `OOMKilled` | 原生识别 cgroup 限制，`MaxRAMPercentage` 按百分比配置 |
| **镜像体积** | 只能塞完整 JRE 的 fat jar，镜像动辄 300MB+ | `jlink` 裁剪运行时 + 分层构建，可降到 1/3；Boot 4 模块化进一步瘦身 |
| **启动速度** | 数十秒级，弹性扩缩容跟不上流量 | AOT + Spring Data 构建期查询编译 + 原生镜像 → 秒级甚至毫秒级 |
| **弹性伸缩** | 慢启动导致扩容滞后、缩容易中断请求 | 快启动 + 优雅停机 + K8s 探针（liveness/readiness）原生支持 |
| **可观测性** | 自研埋点，指标/日志/链路三套割裂 | Micrometer 2 + OpenTelemetry starter，traceId 自动串通 |
| **Serverless / FaaS** | 冷启动无法接受 | 原生镜像冷启动降至毫秒级，见 [[16-Serverless与FaaS]] |

**一句话**：JDK 8 应用能「跑在容器里」，但不等于「为容器而生」。JDK 21 把资源边界、启动速度、诊断能力这三个云原生前提补齐了。

### 2.2 并发能力量级提升（虚拟线程）

对**工业物联网与水务遥测**这类场景，价值尤其直接：

```java
// 海量设备长连接 / 高频上报的同步写法，在 JDK 21 上即可支撑
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    deviceIds.forEach(id -> executor.submit(() -> {
        var telemetry = blockingReadFromDevice(id);   // 阻塞时自动卸载
        return persist(telemetry);
    }));
}
```

| 维度 | 现状（平台线程池） | 升级后（虚拟线程） |
|------|-----------------|------------------|
| 单机并发连接 | 数千级（受线程数与内存限制） | **百万级** |
| 阻塞 IO 代价 | 占用 OS 线程，上下文切换昂贵 | 挂起卸载，carrier 线程复用 |
| 代码形态 | 要么线程耗尽，要么改写为响应式 | **同步写法基本不用改** |

⚠️ **注意配套**：虚拟线程让并发「几乎免费」，也意味着数据库、第三方接口更容易被瞬时打爆。Boot 4 的 `@ConcurrencyLimit` 正是为此而设，应与虚拟线程**成对启用**。

### 2.3 延迟与稳定性（分代 ZGC）

| GC | 典型停顿 | 适用 |
|----|---------|------|
| Parallel GC（JDK 8 默认） | 秒级 | 吞吐优先 |
| G1 GC（JDK 9+ 默认） | 十~百毫秒 | 通用 |
| **分代 ZGC（JDK 21）** | **亚毫秒** | 大堆 + 低延迟 SLA |

对**水务实时监控、工业告警推送**这类抖动敏感业务，GC 停顿从秒级降到亚毫秒，是可以直接写进 SLA 承诺的改善。开启仅需 `-XX:+UseZGC`。

### 2.4 研发效率

- Records / sealed / 模式匹配 / 文本块 → 样板代码显著减少
- Boot 4 内建 API 版本化（RFC 9745）→ 政企项目「多版本接口长期并存」的硬需求有了标准解法
- JSpecify 空安全 + NullAway 构建期检查 → NPE 类缺陷左移
- `@Retryable` / `@ConcurrentLimit` 内建 → 不再自己糊重试与限流

### 2.5 成本（TCO）

| 项 | 方向 |
|----|------|
| 单机吞吐 | 提升 10%–30% → 同等负载可少开实例 |
| 内存占用 | 下降 10%–20%（Compact Strings + GC 改进） |
| 容器资源 | 内存边界准确 → 减少为「保险」而超配的资源 |
| 运维人力 | 自研监控/埋点代码可大幅删减 |
| 商业许可 | 改用 OpenJDK 发行版可**完全规避 Oracle 订阅费** |

## 三、信创与数据合规（本公司场景特有）

结合公司「政府 / 工业 / 水务」的项目属性与「代码数据不出境」的红线：

| 要求 | 应对 |
|------|------|
| **规避 Oracle 许可** | 采用 OpenJDK 发行版：Eclipse Temurin、或**国产发行版 Alibaba Dragonwell / 华为毕昇 JDK / 腾讯 Kona** |
| **信创适配** | 国产 JDK 发行版对龙芯（LoongArch）、鲲鹏（ARM）有官方支持；JDK 21 是各国产发行版当前主推的 LTS 线 |
| **数据不出境** | 全套技术栈均为开源/国产，可完整私有化部署，无境外依赖与遥测 |
| **密码合规** | JDK 21 含 KEM API（JEP 452），为后量子密码迁移预留；国产密码库可通过 JEP 442 外部函数 API 安全调用，替代 JNI 胶水层 |
| **供应链安全** | Boot 4 模块化减少攻击面；配合 CycloneDX SBOM 生成（OpenRewrite Boot 4 配方已含该插件升级） |

> 💡 **选型建议**：JDK 发行版本身采用国产 OpenJDK（Dragonwell / 毕昇）即可同时满足「零许可成本」「信创适配」「数据不出境」三条要求，无需 Oracle 订阅。

## 四、风险与对冲

升级不是没有代价，必须提前计入排期：

| 风险 | 概率 | 影响 | 对冲措施 |
|------|------|------|---------|
| `javax.*` → `jakarta.*` 遗漏（反射/XML/配置文件） | **高** | 启动期崩溃 | 用 OpenRewrite 而非 sed；改完按模块逐个启动验证 |
| Spring Security 自定义鉴权重写 | **高** | 工时超预期 | 单独排期，先做最小可用版本 |
| 第三方依赖无 jakarta 版本 | 中 | 阻塞 | **先做依赖盘点**，识别停更组件并准备替换方案 |
| Jackson 3 默认行为改变 | **中** | 线上 JSON 输出变化 | 用 `spring-boot-jackson2` 垫片渐进迁移；签名/日期相关接口重点回归 |
| 老二方包强封装反射报错 | 中 | 启动失败 | `--add-opens` 仅作过渡，同步推动二方包升级 |
| 虚拟线程下的线程固定（pinning） | 中 | 吞吐不达预期 | 排查重度 `synchronized`，必要时回退 `spring.threads.virtual.enabled=false` |
| 性能未达预期 | 低 | 收益打折 | 升级前后各做一次基线压测，用数据说话 |

**关键前置动作：升级前先做一次完整的依赖盘点**（`mvn dependency:tree` + 停更组件识别），把「有没有 jakarta 版本」这件事摸清楚——这一步的产出直接决定工时估算是否靠谱。

## 五、结论与建议路线

### 结论

**建议升级，且现在是合适的时点。**

- 决定性理由是**风险关闭**而非功能增益：Boot 2.3 与 JDK 8 的组合已无任何官方补丁来源，在强合规行业这是不可长期接受的状态。
- 目标版本应为 **JDK 21 + Spring Boot 4.1**（不是 3.x）：JDK 21 是当前支持周期与生态成熟度最平衡的 LTS；Boot 4.1 是当前唯一处于主流支持期的 Spring 大版本。
- 若项目对信创有明确要求，JDK 采用**国产 OpenJDK 发行版**（Dragonwell / 毕昇）。

### 建议路线

```
阶段 0：准备（1 周）
  └ 依赖盘点、停更组件识别、确定替换方案
  └ 搭建 JDK 21 + Boot 4.1 的空白骨架，验证 CI/CD 与基础镜像

阶段 1：试点（2–3 周）
  └ 选一个非核心、依赖最少的服务走完整流程
  └ 产出：版本对照表 + 踩坑清单 + OpenRewrite 配方定制
  └ 做升级前后基线压测，量化收益

阶段 2：推广（按服务排期）
  └ 按试点固化的清单逐个服务执行
  └ 每升一个服务立即全量回归，不攒批

阶段 3：收尾
  └ 移除兼容垫片（Jackson 2、--add-opens）
  └ 开启 ZGC、虚拟线程（配 @ConcurrencyLimit）
  └ 接入 OpenTelemetry，删掉自研埋点
```

### 一句话决策依据

> 不升级的代价是**持续暴露且无法通过审查的合规风险**；升级的代价是**一次性、可预算、可分期的 10–17 人日/项目**。在政府与水务这类强合规场景中，这个权衡没有悬念。
